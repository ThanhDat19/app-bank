## Review the invariants

- All OPERATOR controls freeze/unfreeze/reversal require immutable request + distinct checker identity.
  Maker/checker are responsibilities in a request, not new global roles; both use existing OPERATOR authority.
- Both actors must differ from target account owner. JWT renewal cannot self-approve; untrusted issuer is rejected.
- Preparing an intent has no account/financial effect. The original client key remains bound even if approval fails.
- Request lock and transaction-bound EXECUTING claim precede existing account/reversal execution. Terminal result,
  effect, linked history, central audit and existing financial outbox/journal commit atomically.
- SQL rejects unfinished EXECUTING, forged approval JSON, unapproved raw account state mutation/new reversal insert,
  mutable intent/terminal result/history and same-identity checker. History links prove the exact intended effect.
- Failed execution or commit restores PENDING, no account/money/journal/outbox/audit partial success. Concurrent
  observers/retries cannot post twice. No network in approval transactions.
- Legacy mutation routes fail409 and application entry points are guarded. Existing GET receipts continue to work;
  maker reads result through operation request; raw reversal receipt belongs to checker/legacy creator.

## Limits for owner review

This deliberately breaks direct mutation APIs; schema/app/clients require coordinated cutover. Pending reversal requests
do not reserve money or promise future approval; state/version/funds/holds may change. All operators can browse requests
and durable results. Audit retains private actor identity while public request/history omit it. A database owner can
disable triggers, and two identities do not prove two humans. No MFA, teams/threshold policies, cash-in/KYC approval,
automatic expiry/worker, forced external UNKNOWN resolution, retention/export or production authorization certification.
